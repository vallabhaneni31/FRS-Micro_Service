## backend/api (primary Node service)

### Stack snapshot
- **Language/framework:** Node.js ESM (`"type": "module"`, `backend/api/package.json:5`), Express 4.21 (`backend/api/package.json:26`)
- **Build/package manager:** npm, `backend/api/package-lock.json`
- **Database:** PostgreSQL, no ORM — raw parameterized SQL via `pg` (`backend/api/src/db/pool.js:1-27`)
- **Test stack:** Node's built-in `node:test` + `node:assert/strict` (`backend/api/src/tests/authzUserProvisioning.test.js:1-2`)
- **Lint/typecheck:** **none configured** — no `.eslintrc*`/`eslint.config*` found, no `lint`/`typecheck` npm script (`backend/api/package.json:5-13`)

### Directory layout
```
backend/api/src/
  config/         # env/config loading (config/env.js)
  controllers/    # PascalCase controller classes — only 13 of ~50 resources have one (see Layering below)
  core/           # clients/, db/, infra/, kafka/, managers/, rules/, services/, util/, workers/
  db/             # pool.js, retailPool.js, migrations/ (37 flat SQL files)
  jobs/           # scheduled/cron jobs (node-cron)
  middleware/     # 17 files: asyncHandler, authz, authenticateDevice, auditLog, rateLimit, keycloakVerifier, correlationId, requestLogger, ...

  routes/         # ~50 files, one per resource
```

### Naming conventions
- Route files: camelCase + `Routes` suffix — `authRoutes.js`, `attendanceRoutes.js`
- Controller files: PascalCase + `Controller` suffix — `AttendanceController.js` (`backend/api/src/controllers/`)
- Service files: camelCase + `Service` suffix — `authService.js`, `tokenService.js`
- Repository files: camelCase + `Repository` suffix — `authRepository.js`, `tenantRepository.js`
- Test files: `<subject>.test.js`, flat under `src/tests/`, test names often ticket-prefixed, e.g. `"AB#2812 - assertUserProvisioned: ..."` (`backend/api/src/tests/authzUserProvisioning.test.js:5`)
- Functions: camelCase, exported route-handler factories are verb-first — `loginWithEmailPassword`, `refreshAccess` (`backend/api/src/routes/authRoutes.js:8-10`)
- SQL migrations: `NNN_snake_case_description.sql`, zero-padded 3-digit sequence — `backend/api/src/db/migrations/` (note: two `002_*` and two `003_*` files coexist from parallel branches — don't assume the numbering is collision-free)
- DB columns/tables: `snake_case` with `pk_`/`fk_` prefixes — `pk_user_id`, `fk_user_id`, `frs_user`, `frs_tenant_user_map` (`backend/api/src/routes/authRoutes.js:180,349,592`)

### Layering — two coexisting patterns `(inferred, needs human confirmation)`
Traced end-to-end via login (`POST /api/auth/login`):
1. Route — `backend/api/src/routes/authRoutes.js:156-211`, mounted at `backend/api/src/server.js:443`
2. Middleware inline in the route def: `authRateLimiter`, `accountLoginLimiter`, `validateBody(loginSchema)`, `asyncHandler` — `backend/api/src/routes/authRoutes.js:157-161`
3. Service — `loginWithEmailPassword()` in `backend/api/src/services/authService.js`, called directly from the route (no controller in between) — `backend/api/src/routes/authRoutes.js:8,165`
4. Repository — `findUserByEmail()` runs parameterized SQL via `db/pool.js` — `backend/api/src/repositories/authRepository.js:1-20`
5. The route handler *also* runs `pool.query()` directly for MFA/session checks — `backend/api/src/routes/authRoutes.js:179-194` — so DB access isn't confined to the repository layer everywhere.

Only 13 of ~50 resources have a `controllers/` file; most routes (auth, alerts, incidents, ...) call services or the pool directly from the route file. **Confirm with the team whether `controllers/` is the convention being adopted for new routes, or a legacy layer being phased out** — new code should match whichever answer that is, not silently pick one.

### Data access & migrations
- No ORM — hand-written parameterized SQL via `pg`, e.g. `backend/api/src/repositories/authRepository.js:4-19`
- Two tenant-isolation models coexist mid-migration: RLS via `withTenantContext()` setting the Postgres session var `app.tenant_id` (`backend/api/src/db/pool.js:1-5`) alongside legacy `frs_tenant_user_map` joins — already documented in `docs/architecture/BACKEND_ARCHITECTURE_OVERVIEW.md:8`, cite that rather than re-deriving.
- Migrations are flat numbered `.sql` files applied by `backend/api/scripts/migrate.js` (idempotent base-schema loader) plus several one-off `run_migration_NNN.js` scripts — **not wired as an npm script**, run directly (`node scripts/migrate.js`).
- Two separate Postgres pools exist in this service: `pool` (core) and `retailPool` (retail) — both imported into `backend/api/src/routes/authRoutes.js:34-35` for a cross-service forgot-password fallback.

### API / interface contracts
- Request validation: Zod, e.g. `listEmployeesSchema` (`backend/api/src/validators/schemas.js:9-31`), applied via `validateBody(schema)` returning `400` with `{message: "Validation failed", errors: ...}` (`backend/api/src/validators/schemas.js:98-110`)
- **Response envelope is inconsistent** — some endpoints return `{success, message}` (`backend/api/src/routes/authRoutes.js:278-281`), others the resource directly (`backend/api/src/routes/authRoutes.js:200`), others `{valid, ...}` (`backend/api/src/routes/authRoutes.js:550-561`). Treat this as an anti-pattern to avoid compounding, not a convention to copy into new endpoints.
- Status codes in use: 200, 204 (logout), 400, 401, 403, 404, 410 (expired/used invite), 500 — see `authRoutes.js` for examples of each.
- OpenAPI is generated via `npm run generate-openapi` (`backend/api/scripts/generate-openapi.js`) `(inferred output location: backend/api/src/docs/, not directly confirmed)`.

### Error handling
- Central error middleware: `backend/api/src/server.js:631-649` — a 4-arg Express handler near the end of the chain, maps known JWT/Keycloak error codes to `401`, everything else to `500` with `{message: "internal server error"}` (stack only in dev).
- `asyncHandler(fn)` wraps route handlers to forward rejected promises to `next(err)` — `backend/api/src/middleware/asyncHandler.js:1-3`
- **No typed error class found** — errors are ad hoc `throw new Error("message text")`, with call sites string-matching on `err.message` for control flow (e.g. `backend/api/src/routes/authRoutes.js:202-208` matches literal account-lockout text). This is fragile; don't extend the pattern in new code without discussing a typed-error alternative.

### Testing
- Full local run: `npm test` → `node --test src/tests/*.test.js` (`backend/api/package.json:9`)
- **CI's actual gate is narrower**: `node --test src/tests/password.test.js src/tests/security.test.js` only (`azure-pipelines.yml:96-99`) — a comment there notes the other ~24 suites need the live stack and run post-deploy. When a spec's acceptance criteria need a test that isn't one of those two, its "passing" status depends on a manual/post-deploy run, not the CI gate — say so explicitly in the spec's test plan.
- No separate integration/e2e directory — all tests are flat under `src/tests/`.

## backend/api-transport (Java — different stack, do not conflate with the Node services)

- Spring Boot 3.3.4, Maven (`backend/api-transport/pom.xml:8-10`), package root `com.motivity.transport`
- Data access: Spring Data JPA + Flyway migrations (`backend/api-transport/pom.xml:42-56`) — a genuinely different pattern from the two Node services' hand-written SQL.
- Auth: `spring-boot-starter-security` + `jjwt` 0.12.6, explicitly *not* `spring-boot-starter-oauth2-resource-server` (`backend/api-transport/pom.xml:60-61,69-86`).
- Package structure: `config/`, `controller/`, `dto/`, `entity/`, `event/`, `exception/`, `kafka/`, `repository/`, `security/`, `service/` — standard layered Spring Boot shape.
- Tests: JUnit classes under `src/test/java/.../controller/` (e.g. `AttendanceApiTest.java`) `(inferred: run via mvn test, standard Spring Boot convention — not independently confirmed)`.
- Not built by this repo's `azure-pipelines.yml` — moving to its own repository (`azure-pipelines.yml:8-11`).
- Error handling, DTO shape, and other Java-specific conventions were not scanned in this pass — read `exception/` and a controller before writing Java code here.

## Don'ts (observed anti-patterns — don't extend these)
- Don't add another inconsistent response shape — pick one of the existing shapes deliberately or raise the inconsistency, don't add a fourth.
- Don't control flow by string-matching `err.message` — no typed error class exists yet; flag this rather than copying the pattern into new call sites.
- Don't assume `npm test` is what CI checks for `backend/api` — it isn't (see Testing above).
