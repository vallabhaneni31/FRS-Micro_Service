## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

## Working agreement (coding-agent contract)

1. **Inspect before assuming** structure or stack — the code is the source of truth.
2. **Smallest correct change**, matching the surrounding file's naming, layering, error handling
   and tests. `backend/api` has two coexisting layering patterns (route→service→repository, and
   routes calling services/pool directly) — see `docs/PATTERNS.md` before picking one.
3. **ASK rather than guess on contracts** — API shape, data model or migration, error/status codes,
   scope boundary, compatibility.

## Spec-driven development

Non-trivial **feature** changes start with a reviewable spec — see `specs/README.md` and
`specs/AGENTS.md` for the current process: `/edith-spec <feature>` writes a spec **folder**
`specs/NNNN-slug/` (`requirements.md` with EARS-notation acceptance criteria, `design.md`,
`tasks.md`), `/edith-spec-review` for adversarial review, `/edith-spec-build` to implement
task-by-task, `/edith-status` for the board. This replaced an earlier single-file
`specs/NNNN-slug.md` convention — `specs/TEMPLATE.md` is a leftover from that and no longer
matches actual practice; nothing currently uses it.

**Bug tickets use the existing `docs/BUGFIX_WORKFLOW.md` process instead** (Azure Boards `AB#<id>`,
branched off `allbugfix`) — that process is unchanged by either spec convention.

## Git & PR workflow

- Branch off the default branch; never commit straight to it.
- Before a PR: quality gates pass (see Stack above for what those actually are in this repo),
  `/code-review` is clean, every acceptance criterion has a passing test.
- No AI attribution in commit/PR history — enforced via `.claude/settings.json`'s `attribution`
  keys (empty), not just this instruction.
- Only commit or push when the human asks; surface the diff for review first.
